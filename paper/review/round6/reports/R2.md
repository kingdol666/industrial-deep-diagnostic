Reviewer focus: §2 motivation, §3 system architecture, Table 2 module contracts, Table 3 checkpoint
predicates, engine layer (14 engines, typed errors), agent personas/model assignment, §3.2/3.3

against the actual repository (orchestrator skill, backend engine layer, OMP agent frontmatter,

## 1. Overall assessment

This is, by the standards of applied engineering-informatics submissions, an unusually *verifiable*
systems paper. The three properties my taste demands — unmistakable module responsibilities, an
explicit collaboration contract, and truthfulness of every system statement — are mostly present,
and, critically, they are mostly **true of the released code**. I verified the following
load-bearing claims against the codebase and they hold exactly:

- **Nine-stage pipeline, stage order, agents, artifacts.** Fig. 2 (p-14) and §3.3 match
  `.claude/skills/industrial-analysis-auto/SKILL.md` (Pipeline Flow, lines 52–75; Sub-Skill Map,
  lines 79–89): Step 0/1 main agent → Step 2+2.5 context-builder (CP-2/3) → Step 3 data-processor
  (CP-4) → Step 3.5 VLM → Step 4 diagnostician (CP-5) → Steps 5a/5b judge ∥ physical pre-audit
  (CP-6) → Step 6 reporter (CP-7) → Step 7 final audit (CP-8 ENDORSED) → Steps 8/8.5 HTML build +
  review (CP-9) → Step 9 finalize. The "only parallel step" discipline, the HTML auto-build after
  CP-8, and artifact-only inter-agent communication (SKILL.md:200, 455, 484–498) are all stated in
  the paper exactly as implemented.
- **Table 3 (CP-1..CP-9) is correct — every predicate, transition and failure action matches
  SKILL.md:436–446 line for line**, including the numeric bounds (ontology ≥1 KB, plots > 0,
  html ≥ 5120 B) and CP-6's "judge_repair_summary.json + pre-audit no FATAL".
- **14 engines and the uniform contract are real.** The `ENGINES` dispatch table
  (`app/backend/src/services/diagnosis.service.mjs:45–72`) has exactly the 14 ids the paper lists
  (claude, omp, mock, codex, opencode, dsh, hermes, qwen, gemini, copilot, cursor, crush, goose, pi)
  and each entry exposes exactly the five methods the paper names
  (startDiagnosis/startSessionChat/parseStreamEvent/registerChild/closeQuery). `HARNESS_DEFS`
  (`app/backend/src/harness/engines.mjs:21–142`) + the claude/omp registrations
  (`registry.mjs:11–12`) are the single source of truth as described; the mock engine is in-process
  and always available (engines.mjs:23–31), matching the "CI without external dependencies" claim.
- **Typed errors are real and exact**: `HarnessUnknownError` → 400 `HARNESS_UNKNOWN`,
  `HarnessUnavailableError` → 409 `HARNESS_UNAVAILABLE` with a human-readable command-override hint
  (`app/backend/src/harness/availability.mjs:15–32`); probing and spawn share `resolveCliBinary`
  (`engine/cli-common.mjs:6,86`), exactly as §3.1/§3.4 claim.
- **Repair governance** (best-of-3 with best_round snapshot, global cap 5 counted via
  `repair_spawn` events, anti-oscillation 3rd oscillation → COMPETING_SET cap 0.50, never halt on
  score) matches SKILL.md:352–370 and 465–473. A released `judge_repair_summary.json`
  (`workspace/diagnostic-runs/202609150453290_bench_skab_valve1_1/05_review/`) shows the mechanism
  live: repair_rounds_used 0, best_score 90, CP-6 note "judge pass(90) + preflight PREFLIGHT_PASS
  (no FATAL)".
- **Knowledge/network/enhancement layers** (§3.2) check out: RAG microservice on port 8764
  (`rag-retrieval-engine/server.py:9,960`), Step-0 three-second health probe
  (`curl -m 3 http://localhost:8764/health`, SKILL.md:225–228), `parameter_to_physics.json`
  fallback map (exists in `industrial-ontology-builder/resources/`), ontology asset store with
  `publish` + deterministic `fast-reuse` (`.claude/shared/scripts/ontology_store.mjs`; SKILL.md
  Steps 2-F/CP-2 publish). RAG degradation is recorded in run events (e.g.
  `"rag":"fallback_directive"` in the context_builder step_start event of
  `202609150454126_bench_tep_d01_ac_feed_ratio/.pipeline_events.jsonl`). Web app ports 3210/5180
  and SQLite WAL (`config/default.yaml:9,14,21`; `db/database.mjs:11`) are correct.
- **Model assignment**: among the 14 `.omp/agents/*.md`, only `vlm-visual-analyzer.md:4` declares
  `model: vision`; the diagnostic-path agents declare `model: default` (the enhancement-layer
  trio declares `sonnet` and sits outside the benchmarked path, as the paper says). This matches
  §6.4's disclosure that the vision stage executed its non-visual degradation — visible in the run
  dirs as `visual_analysis.agent_skeleton.json` with
  `analysis_provenance.source_agent = "visual_analysis.py"`, stage `skeleton_pre_vlm`.
- **Provenance labels (C3) are real**: `results/benchmark/gradings/skab_valve1_1.json` carries
  `judge_score_source: "judge-agent-10-criteria"`, `audit_verdict_source: "auditor-agent"`,
  `html_review_source: "html-reviewer-agent"`.
- **Run-dir layout and naming**: `workspace/diagnostic-runs/<ts>_bench_<case>/` exactly as Appendix
  Table A2's caption states; every Consumes/Produces filename in Table 2 exists in the released run
  directories (verified in the canonical 2026-09-14 run `202609141511399_bench_skab_valve1_1` and
  the graded 2026-09-15 run `202609150453290_bench_skab_valve1_1`), including the three
  HTML-build artifacts in the manifest-first order (enforced in
  `industrial-html-visualizer/SKILL.md:3,8,51–56`).

Because the paper explicitly invites filename-level scrutiny ("filenames as released", "the same
fourteen filenames appear in the released run directories"), the few places where the enumeration
does **not** match the enforced reality stand out and must be fixed. They are all one-line
corrections; none undermines the results.

## 2. Must-fix (blocking)

**MF-1. Five-factor confidence weights are stated wrongly (§4.1, p.17–18; main.tex:284).**
The paper says the factors are "weighted 25/20/20/20/10, totalling 100, in the released
`confidence.json`". The released `confidence.json` says otherwise, and so does the code that
enforces it:
- `workspace/diagnostic-runs/202609141511399_bench_skab_valve1_1/04_diagnostics/confidence.json` —
  H1 `five_factor_breakdown` maxes: statistical_strength 25, physical_plausibility 25,
  temporal_evidence 20, absence_of_confounds 20, symptom_completeness 10 (i.e. **25/25/20/20/10**).
- `.claude/skills/industrial-diagnostician/scripts/diagnostic-quality-check.mjs:151`:
  `factorMax = { statistical_strength: 25, physical_plausibility: 25, temporal_evidence: 20,
  absence_of_confounds: 20, symptom_completeness: 10 }`; same maxes in
  `scripts/confidence-completeness-check.mjs:55–61`.
- Note the diagnostician's own `references/agent-protocol.md` (Phase 6 table) contains a *third*
  variant (20/25/20/20/15) — the repository should be reconciled and the paper must state the
  machine-enforced weights (25/25/20/20/10). A numeric contract that the paper grounds in "the
  released confidence.json" is falsified by that very file; this is exactly the class of error the
  paper cannot afford.

**MF-2. Appendix Table A2 lists a released path that does not exist (p.66; main.tex:694).**
Row 2 claims `00_input/brief.json` ("blind evidence pack … leakage-sentinel checked") relative to
"each released run directory `workspace/diagnostic-runs/<ts>_bench_<case>/`". No run directory
contains any `brief.json` (verified by `find` over all of `workspace/diagnostic-runs`). The blind
briefs live at `results/benchmark/briefs/<case>.brief.json` — a different tree with a different
filename convention. Fix the path (and note that `00_input/` additionally contains
`run_config.json`, `clarification_needed.json`, `input_inspection.json`, which the index omits).

**MF-3. The "fourteen items" of the completeness gate are off by one member (§5 C4 + Table 4,
p.25; main.tex:332, 338–363).** The enforced grader-side list is `PIPELINE_ARTIFACTS` in
`scripts/benchmark/zcode_direct_pipeline.mjs:288–303`: 14 entries **including
`diagnostic-report.html` and NOT including `optimizer.md`** (plus a `<5120 B` size re-check in
`pipelineMissing`). The paper's Table 4 includes `optimizer.md` and omits
`diagnostic-report.html`. All 14 paper-listed files do exist in the released run dirs (so the
"appear in the released run directories" sentence is true), and the ENDORSED requirement is
enforced at grading via `audit_verdict` — but the caption "The graded artifact set enforced by the
completeness gate" is an enumeration claim, and for a paper whose thesis is machine-checkable
artifact contracts the enumeration must be the enforced one. Correct the table (or list the gate's
14 exactly and state separately that grading additionally requires the ENDORSED verdict).

## 3. Should-fix (non-blocking)

**SF-1. Algorithm 1, line 10 (main.tex:300): "finalise—14-artifact inventory".** The Step-9
finaliser's own inventory is ~45 checks (`pipeline-finalize.mjs`, section comment "STEP 1:
Artifact Inventory (~45 core checks)"), covering critical and non-critical items; "14" is the
*grader's* list. Reword ("full artifact inventory" or "~45-check inventory") to avoid a third
competing count.

**SF-2. §3.1 (main.tex:127): "the diagnostic path … uses nine of them [skill packages]"
followed by a list of nine *agent* names.** Steps 2–8.5 dispatch eight sub-skills
(SKILL.md Sub-Skill Map); the VLM stage executes inside the data-processor skill (Phase 5.5), and
the ninth skill on the path is the orchestrator itself. The counts are defensible but the sentence
conflates the skill and agent inventories; disentangle ("eight dispatched sub-skills executed by
nine agent types").

**SF-3. "The pipeline's only parallel step" (§3.3, §4.6).** True per SKILL.md:455 for the
*mandatory* flow, but the same orchestrator defines an optional Step 2P data-profiling pre-pass
dispatched in parallel with Step 2 (SKILL.md:311–313). One clarifying clause ("the only mandatory
parallel step") makes the claim exactly true.

**SF-4. §3.2 "falls back to … `parameter_to_physics.json` … plus web search".** Under the Step-0
fast-fail protocol the ontology builder "goes straight to the `parameter_to_physics.json` fallback
path and **skips** Phase 2/3 … avoids … idle web-search spinning" (SKILL.md:229), while the
Failure-Recovery table (SKILL.md:566) still says "+ web search". The repo is internally split; the
paper should state which variant is protocol (the benchmark logs suggest the skip variant).

**SF-5. §6.4 harness disclosure "the ZCode agent CLI (the CLI-driver class of the engine layer)".**
No `zcode` id exists in `HARNESS_DEFS`/`ENGINES`; the benchmark was driven by
`scripts/benchmark/zcode_direct_pipeline.mjs`, which sits beside the backend dispatch table. The
wording is defensible but one sentence making explicit that the benchmark driver is external to the
14-engine registry would pre-empt a checker finding the id missing.

**SF-6. §3.2/§7 "the degradation is recorded in the run events".** Verified in the current-era
graded runs (`"rag":"fallback_directive"`), but the 2026-09-14-era event logs contain no rag event
at all. Make the claim era-precise, or point to where the earlier era records the probe outcome
(`prepare_digest.json` / run_config), since the paper leans on "both recorded".

## 6. Verdict

The paper's system description is, with three exceptions, a faithful and unusually checkable
account of the released system: the checkpoint table, module contracts, engine layer, error
contracts, layer ports, model assignment, and repair governance all verify against code and
artifacts. The exceptions (five-factor weights, one released-artifact path, the completeness-set
enumeration) are precisely in the register the paper itself stakes its credibility on — machine-
checkable contracts stated to the filename and the integer — so they are blocking, but all three
are one-line corrections that require no re-execution.

**Recommendation: MINOR_REVISION.**
