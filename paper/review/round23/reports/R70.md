## 1. Summary of findings

I read the full paper source (`paper/main.tex`, 765 lines) and the rendered pages for my
focus areas (pp. 6, 8–16, 20, 24, 26–29, 33, 35–38, 40–41 of `paper/review/round23/pages/`),
then performed **26 claim-vs-reality checks** against the codebase, the 12 canonical grading
records, the 12 canonical run event logs, the run journal, git history, and the released
benchmark artifacts. **Every load-bearing claim in my focus areas is TRUE of the released
system.** I found no factual mismatch. The residual items are presentational (Section 5).

The paper's distinctive property — and the reason it survives a hostile systems audit — is
that its architecture section is written as a set of falsifiable, machine-checkable statements
(18 packages / 12 checklists / 8 dispatched / 6 without; twelve-entry capability table + two
first-party wiring entries; "3+3.3" dispatch label; run-dir numerals UTC; eleven-of-twelve
markers), and every one of those counts is exactly right in the repository.

## 4. Strengths (systems-reviewer view)

1. Unusual audit resistance: the paper states counts and mechanisms precisely enough to be
   falsified, and they hold (census, engine table split 12+2, dispatch label, UTC numerals,
   marker census, journal chronology to the tenth-of-a-second, commit timestamp in UTC).
2. Execution form is disclosed, not laundered: inline stage execution, the missing spawn
   tool, the shared-session corollary, and 5a‖5b serialization are all stated in §5 and are
   exactly what the logs record — including the paper quoting the logs' own reason strings.
3. Honest negatives retained in the system description: RAG channel degradation per run,
   non-visual VLM deployment, the single L5/L6 corroboration-only item, one control with a
   repair round, the one scenario whose log lacks a marker.
4. Module contracts are real: Table 2 filenames, Table 3 checkpoint predicates, and the
   14-artifact completeness set each map 1:1 onto skill files, SKILL.md tables, and
   `PIPELINE_ARTIFACTS`.

## 5. Issues

### MUST-FIX (blocking)
None. I could not falsify any §2–§6 claim I tested (26 checks, all match).

### SHOULD-FIX (non-blocking)
1. **§5 (p.28), marker sub-split wording.** "a dedicated field on eight runs, disclosure or
   remediation notes on three" — my census of the canonical logs reads ~9–10 runs carrying
   dedicated inline* fields and ~2 carrying only note-style markers (skab_normal_control's
   `note`, tep_d01's `remediation`/`disclosure`), depending on how `harness:"inline-degraded"`
   (tep_d00) and `harness_disclosure` (tep_d04) are classed. The load-bearing count
   (eleven of twelve; only skab_cavitation_13 lacks one) is exact. State the classification
   criterion (e.g., "a field whose name or value is dedicated to execution form") or give the
   per-run key list in a footnote/appendix.
2. **§3.1 (p.10), first architecture sentence.** "sub-agents communicate only through
   workspace artifacts, never through conversation context" is a property of the dispatch
   form; in the benchmarked inline form it did not literally hold (disclosed only as a
   "corollary" in §5). §3.3 already points forward to §5; add the same forward pointer at
   this first occurrence.
3. **Table 4, row "Commit 221d061".** The commit's subject line is about baseline
   reproduction; the calibrated keyword set is pinned *at* that commit (per
   keyword_sensitivity.json `calibrated_keyword_commit`). "formalizes" slightly overstates
   the commit message; "pinned at" would be exactly right.
4. **Fig 5 (p.41).** The two annotation boxes overlay the flow trace; nudge above/below the
   band for print cleanliness.
5. **§3.2 (p.12).** "the two other SKAB runs (cavitation and the normal control) lack the RAG
   artifact via the same fast path" — verified; consider adding the one-line evidence key
   (absent `00_input/rag_deep_understanding.json` + zero rag events) to make this claim
   reader-checkable without log access.
