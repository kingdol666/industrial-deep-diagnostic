# R10 — Industrial-Informatics Systems Review (Round 8, blind)

Reviewer mandate: every statement the paper makes about the system must be TRUE of the real
codebase; architecture, modules, and collaboration must be unmistakably clear. Focus: §2–§3
architecture narrative, engines/typed errors, repair governance, RAG layer, model assignment.

Reviewed: `paper/main.tex` (72 pp), rendered pages `paper/review/round8/pages/p-05..p-18.png`,
ground truth under `.claude/skills/`, `.omp/agents/`, `app/backend/src/`, `rag-retrieval-engine/`,
`workspace/diagnostic-runs/`, `results/benchmark/`. I read nothing else under `paper/review/`.

---

## 1. Overall assessment

The §2–§3 architecture narrative is, with one exception (RAG classification of the canonical
tep_d14 run, below), an unusually faithful description of the released system. The three
"scoping clarifications" in §3.1 (18 skills / 14 agents with an 8-specialist diagnostic path;
skill package = protocol + schemas + validators, not a prompt; 14-engine uniform contract) each
check out exactly against the repository. The checkpoint table is verifiable line-by-line. The
one genuine claim-vs-reality mismatch I found is a single sentence in §3.2 that misfiles the
canonical TEP IDV14 run under "retrieved successfully" when that run's own RAG artifact records
`rag_available: false` with a fallback reason. Layout in the compiled review-format PDF has two
defects (a near-empty page 16; floats drifting 3–4 pages from first citation, contradicting the
paper's own preamble comment).

Verdict: MINOR_REVISION — the blocking fix is one sentence; everything else I checked is exact.

## 4. Architecture clarity (AEI taste)

The three-plane story (engine layer → orchestrator with skill packages → nine-stage gated
pipeline over an audit plane) is genuinely clear, and the paper's honesty devices — three
scoping clarifications, the "diagnostic path vs optional layers" split, the Step-3.5/Phase-5.5
numbering disclaimer — do real work: a reader can map every sentence to a file. The
skills-vs-agents split (18 packages, 14 agents, 8 dispatched specialists) is exactly right and
is the paper's best architectural disclosure. Two clarity nits: (i) "rather than as a separate
dispatch" (§3.1) could be misread as "the VLM is never sub-dispatched"; in fact data-processor
makes a nested `Agent()` call to vlm-visual-analyzer *inside* Phase 5.5
(data-processor SKILL.md:78,131-137) — one clause would fix it; (ii) the paper's "pipeline
Step 3.5" is labelled "Step 3+3.3" in the orchestrator SKILL.md (the Phase-5.5 mapping is what
matters and is correct; add the alias in a footnote).
