## 4. Findings

### MUST-FIX (blocking)

- M1. §5 Execution form (p. 28): "eight of the twelve canonical run logs carry an explicit
  marker" is factually wrong — the verified count is eleven of twelve (8 runs with dedicated
  fields: valve1_1 `inline_execution`, d00 `harness:"inline-degraded"`, d01 `disclosure`,
  d03 `inline_non_agent_harness`, d04 `harness_mode:"inline"`, d07 `inline_substituted`,
  d11 `inline_no_agent_tool`, d14 `inline_strict_protocol`; plus disclosure notes in batch001,
  batch093, skab_normal_control). Only skab_cavitation_13's log carries no marker. Correct the
  count and the field/note split; the corollary and conclusions are unaffected (direction is
  conservative), but a checkable number must be checkable-correct.

### SHOULD-FIX (non-blocking)

- S1. Fig. 1 / §3.1: add a one-line note that the benchmark driver invokes the CLI-driver class
  directly, bypassing the engine registry (cross-ref §5/§6.4), so the architecture figure and
  the benchmark execution path cannot be misread as the same arrow chain.
- S2. §5: after correcting M1, name the single unmarked run (skab_cavitation_13) explicitly —
  it makes the disclosure fully reproducible by a reader.
- S3. §3.1's unconditional "sub-agents communicate only through workspace artifacts, never
  through conversation context" is a dispatch-form invariant; under the disclosed inline form
  the invariant holds at the artifact-contract level, not at the model-context level. One
  clarifying clause (the §5 corollary already implies it) would remove the last ambiguity.
- S4. §5/§6.4: "the sub-agent dispatch itself is exercised by the production web harness" is
  supported by the harness/agent code, but the released corpus (all 40 run dirs are `bench_*`)
  contains no execution trace demonstrating Agent-tool sub-agent dispatch. Release or cite one
  production-harness event log to close the loop.
- S5. §3.1 "most also ship the JSON Schemas and validation scripts": replace the vague
  quantifier with the exact per-package census (one line, same verifiability standard as the
  checklist count).
- S6. §6.4: the sentence beginning "the entire chain … is driven by a single entry point" starts
  lowercase after a period ("… median ≈109 minutes across the twelve canonical runs; event-log
  spans). the entire chain …") — typo on p. 32 (source main.tex line 437).

### Positive observations (for the record)

- The §2–§3 architecture description is, with the single M1 exception, byte-level accurate
  against the codebase: every count I checked (18/14/12/8/6, 12+2 engines, CP predicates,
  25/25/20/20/10, 0.70/0.65/0.50, 0.90/0.70 gate, ≥2 eliminations, 14 artifacts, 153-file
  convention, z=1.96) reproduced exactly.
- The execution-form disclosure (inline execution, shared-session corollary, §6.4 driver
  sentence) is honest, internally consistent with §3's dispatch description, and verifiable
  from the released logs — exactly the disclosure discipline AEI expects.
- Repair governance and ceiling enforcement are not narrative: they are re-runnable from the
  released scripts and confirmed by the released per-run artifacts.
- The one repair round in the corpus is where the paper says it is (batch001 control), and the
  §7.3 narrative matches the log.
