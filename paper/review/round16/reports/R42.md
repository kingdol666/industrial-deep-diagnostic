## 2. Findings

### MUST-FIX (blocking)
1. **§6.4 / §3.1 (Benchmark configuration disclosure) — harness execution mode not fully disclosed.**
   The released event logs of canonical TEP IDV3 (`202609141846195_bench_tep_d03_hard`,
   `harness_mode: "inline_non_agent_harness"`) and TEP IDV7 (`202609141854457_bench_tep_d07_header_pressure`,
   `"inline_substituted"`) carry the disclosure "Agent tool not exposed/unavailable in this environment;
   every stage executed inline STRICTLY under its own skill protocol (persona, phases, schemas, scripts,
   gates) with per-stage artifact ownership". I.e., in at least these graded runs the eight-specialist
   sub-agent dispatch that §3.1–§3.3, Fig. 1 and Table 2 present as the execution model did NOT run as
   separate agent dispatches; stages ran inline in one session under the same per-stage protocols
   (artifact ownership and gates demonstrably held — finalize PASS, all Table 2 artifacts present).
   The paper discloses the harness ("ZCode agent CLI, CLI-driver class… zcode_direct_pipeline.mjs") but
   never surfaces this inline mode or states which canonical runs used dispatch vs inline execution.
   For a paper whose central contribution is a machine execution proof, the execution-proof plane itself
   must state this in text. Fix: one or two sentences in §6.4 (and a pointer from §3.1) quoting the
   logs' own harness_mode disclosure and stating the dispatch/inline split across the twelve runs.

### SHOULD-FIX (non-blocking)
1. Fig. 1 (p.13): after `\resizebox{\textwidth}` the engine-row text is near the print-size floor;
   shorten the engine name row or drop the third sub-line.
2. Table 2 caption (p.17): the trailing "Checkpoint predicates: Table 3." wraps so "Table 3." lands
   alone above the header rule; rephrase or hard-break the caption.
3. p.16 is ~55% empty because Tables 2–3 floated forward; consider relocating §3.5 text or tuning
   float parameters for the final build.
4. §3.2's RAG-engagement paragraph packs ~10 run-level facts into one paragraph; a small per-run
   table (run × RAG outcome) would serve readers better and pre-empt misreading.
5. Model assignment completeness: three enhancement-layer agents carry `model: sonnet`
   (.omp/agents/{deep-analyst,enhance-orchestrator,physics-bridge}.md); one clause in §6.4 would make
   the "only VLM on vision" statement complete.
6. §3.1's parenthetical engine-class gloss ("DeepSeek/Hermes/Qwen ACP dialects…") is code-accurate but
   id≠vendor for `dsh`; consider naming the ids as in Fig. 1 to avoid a second naming scheme.

## 3. Overall assessment

Within my remit (§2–§3 and the graded-run traceability of architecture claims), this is an unusually
truthful systems paper: every census, label, threshold, predicate, filename, and per-run degradation
fact I checked reproduces exactly from the released code and run artifacts — including unflattering
details (RAG failed or was bypassed in 11 of 12 runs; the single L6 item is corroboration-only;
one verdict-type compliance miss). The one substantive gap is the harness-mode disclosure: the
multi-agent dispatch narrative of §3 is the system's real contract, but the released execution proofs
of at least two canonical graded runs attest an inline, non-agent harness mode that the paper never
names. That is a transparency omission fixable with two sentences, not a validity problem — the gates,
artifact ownership, and stage protocols are attested in the same logs. Figures 1–2 and Tables 2–3 are
print-adequate with minor cosmetic nits.

VERDICT for my scope: MINOR_REVISION.
