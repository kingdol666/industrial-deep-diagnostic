## 0. 结论摘要

**系统的工程实现是真的，论文的实验声明有一处致命缺陷和若干处不一致。**

| 层面 | 判定 |
|---|---|
| 管线 / Harness / 前端工程实现 | ✅ 无问题（116/116 后端、64/64 Harness、40/40 本体、26/26 侧边栏） |
| 基准代码链 | ⚠️ 可运行，但**不执行多 agent 管线**，且**输入含真值泄漏** |
| 论文实验声明 | ❌ **C1 致命**：核心对比建立在泄漏输入之上；多处声明与仓库实际不符 |
| 论文可复现声明 | ❌ 声称的 delete-and-rebuild 审计**无任何实现脚本** |
| 论文与仓库一致性 | ❌ 支撑文档描述 32/8 场景，论文是 12，三套数字互不匹配 |

**最严重的一句**：论文摘要与 §4 (C1) 声明 "Ground truth never enters the inference context"，
但实际下发给诊断 agent 的 `process_description`（即 brief 的组成字段）：

- **6 个 TEP 故障场景中 5 个直接写出故障答案**（4 个连评分关键词都写在题面里，
  1 个直接点名 `IDV 3`）；
- 另有 2 个场景（IndPenSim、SKAB 各一）的关键词是**通用工艺词**，任何泛泛诊断都会命中；
- 评分器是 `kw.some(...)` 的 **OR 语义**，命中任一弱词即判 Top-1 正确。

**即 9 个故障场景中至少 5 个的得分不可采信；只有 `tep_d01`、`skab_cavitation_13`
两个故障场景在协议上是干净的。** 因此 TEP 的 6/6 与"对 FaultExplainer 的超越"
**无法排除"照抄题面"解释**——这是审稿人一定会要求补做的实验，且**改措辞无法消除**。

## 0b. 第二轮发现的**产品缺陷**（已修复）

第一轮聚焦"论文声明 vs 证据"。第二轮改为**直接检验评分与产物本身**，发现三处真实的
生产缺陷——即基准数字之外的、会影响任何真实作业的 bug。

### D1 — "10 维质量门"根本不是判断（**最严重**）

`scripts/benchmark/zcode_direct_pipeline.mjs:503` 把十个维度全部写成同一个数字：

```js
criteria_scores: Object.fromEntries(CRIT.map(k => [k, { score: Math.round(note.judge.score / 10) }]))
```

实测 12 次运行**每个维度都恰好是 9**，因此每个场景的"10 维质量门"都是 90——
报告的 mean 91.0 只是在复述**被评产物自己对自身的评价**。该 gate **零判别信息**，
论文所称"10-criterion quality gate"无任何独立评分支撑。

**已修复**：新建 `scripts/benchmark/audit-structural.mjs`——独立于 note、直接检验
12 个 run 的实际产物是否具备每个维度所依赖的证据（证据层级/来源、置信区间、
falsification、反假相关块、四条件、三态类型、COMPETING_SET 置信上限等）。
结果已并入 `metrics.json`（`structural_audit`）与 `report.md` §5。

> **诚实说明其边界**：该审计是**地板（floor）**，不是**排名**。修复后 12/12 均为 100 分，
> 即它只能证明"产物完整、证据可追溯、三态与上限自洽"，**不能区分结论对错或好坏**。
> 自报分数 90/91/92 的差异在产物结构中**找不到任何对应物**——这正是问题所在。

### D2 — `Infinity` 使 `validate_report.json` 不是合法 JSON

`anti_spurious.py` 在零中位数列上算出 `mean_median_ratio = float('inf')`，
经 `json.dump` 写出**裸 token `Infinity`**。这不是合法 JSON：
Python 的 `json.load` 默认接受（`parse_constant`），但 **JS `JSON.parse`、jq、Go、Rust 全部拒绝**。
影响 2 个 IndPenSim run（`Acid flow rate(Fa:L/h)` 等驱动量在批次大部分时间为 0）。

**已修复**：`mean_median_ratio` 改为 `None`（无限比值在数学上未定义，`None` 才诚实，
且 `is_heavily_skewed` 仍正确置真——已单测验证）；并在 `stats/run.py` 的序列化边界加
非有限值→`null` 的防御性转换 + 计数告警，杜绝此类回归。

### D3 — `math domain error` 导致统计层**静默降级**（**这是 8.1 之外的第二个真缺陷**）

`_pearson_simple` 的分母 `sqrt[(n·Σx²−Σx²)(n·Σy²−Σy²)]` 是两大数相减，
浮点抵消可使其**微负**（如 −1e-12），`math.sqrt` 抛 `ValueError: math domain error`，
**整个统计管线中止**，于是 `indpensim_batch093` 退化为 `driver-js-fallback`：

- **完全跳过反假相关校验**（lag CCF / 分布 / 杠杆 / 趋势混杂 / Simpson / 多重检验）；
- 这是 9 个故障场景中的 IndPenSim 故障场景——**论文 §8.1 之外的第二个真实降级**；
- 更糟的是**降级是静默的**：该 run 仍被判为 `finalize PASS`、仍被计分，
  `judge=90`、`control_pass` 等指标照常产出，只有打开 run 目录才能发现。

**已修复**：判别式 ≤0 时返回 0.0（负判别式只意味方差数值为零，无任何可解释性）。
修复后该 run 的统计管线**完整跑通**，产出 982 KB 的完整报告，
`anti_spurious` 全块齐备（strict `JSON.parse` 通过），`execution_integrity.by_engine`
从 `stats-package 10 / driver-js-fallback 1 / unknown 1` 变为 **`stats-package 12`**。

**仍未修复（建议）**：管线**未把统计降级视为阻断条件**。建议在 `validate_report.json`
含 `engine: driver-js-fallback` 时置 `checks.degraded = true`，并让 finalize 阶段
显式要求该标志，使降级无法再静默通过。

### D4 — 控制组通过判据是**散文正则**

`zcode_direct_pipeline.mjs:611`：

```js
const normalClaim = /正常|normal|无异常|无故障|稳态|baseline|稳定/i.test(note.primary_finding + " " + surviving.map(h => h.name).join(" "));
```

控制组"通过"= 结论文本里出现"正常/稳态"等词。三个控制案例**实际结论都是正确的**
（逐条读过 note，均正确判定为无故障基线运行），但该判据与 C1b 同源：
**一个词就能决定一个一级指标**，且与 `diagnosis_type` 无关。

### D5 — `DETERMINED` 一码二义（论文措辞风险）

三个控制组 note 的 `diagnosis_type` 都是 `DETERMINED`，因为协议用它表示
"**得出了明确结论**"——而这里的明确结论恰恰是"**运行正常**"。
于是 `DETERMINED` 同时表示"确定了故障"和"确定了正常"。

论文若把它与"识别出故障"并列，**审稿人会以为三个对照组也被判为有故障**。
论文必须写明这一语义，或为正常判定单列类型。

### D6 — 我自己的审计器曾有 3 处假阳性（已修正）

记下来以免后人重犯：`overall_confidence` 是 `{score,level,summary}` 对象
（`confidence_schema.json` 明确规定），不是 0–1 浮点；`diagnosis.hypotheses` 是
`{surviving, competing_sets, eliminated}` 对象，不是数组；role 有**两套**枚举
（signal: `target/predictor/confounder/control/metadata`，metadata_columns:
`batch_id/product_code/timestamp/operator`）。三处修正后 12/12 全过。

**四重后果**：

1. 论文 §4 (C1) "Ground truth never enters the inference context" 与 §8 "truth isolation"
   的声明**被自己的工件直接否证**（5/6 TEP 场景）。
2. 评分是关键词命中（`zcode_direct_pipeline.mjs:603-604`：`text.includes(kw)`）。
   因关键词**就在题面里**，agent 只需复述输入即可得分 →
   `d04/d07/d11/d14` 四个场景的"正确"**完全无法与"照抄题面"区分**。
3. `d03` 是更硬的一种：题面直接点名 **IDV 3**，而 TEP 故障编号表是公开知识，

4. `indpensim_batch093` 的关键词（曝气/溶氧/流加/pH）是**该工艺的通用变量名**，
   非故障标识 → 任何泛泛的发酵工艺诊断都会命中，**该场景的得分同样虚高**。
   同理 `skab_valve1_1` 的"阀"是通用词。

**只有 `tep_d01`、`skab_cavitation_13` 两个故障场景在协议上是干净的**（外加 3 个对照）。
即：**9 个故障场景中至少 5 个（4 个确定为答案泄漏 + 1 个关键词过泛）的得分不可采信。**

**为什么这是致命的**：论文的核心卖点是"在无候选清单的更严苛设定下超越 FaultExplainer"。
若题面已给答案，则该对比不成立。审稿人只要抽读一个 brief 就会拒稿。

**唯一可接受的修复**：从 `process_description` 中删除一切故障身份信息
（只保留介质、设备拓扑、列语义、采样率、故障时段起止），
**然后用去泄漏后的 brief 重跑 S3 推理**，重新生成全部 12 份 note 与评分。

**同时必须修复评分关键词**：`indpensim_batch093` 的 `aeration/曝气/do2/溶氧/feed/流加/ph`
与 `skab_valve1_1` 的 `阀` 属通用工艺词，不能作为故障标识。
关键词须改为**判别性**词项（例如 IndPenSim 应为具体偏差类型，
SKAB 应为"入口/节流/关阀"组合而非单独"阀"），并补"仅命中通用词不得分"的断言。

### 🔴 C1b（致命，与 C1 同源）关键词匹配过宽：单一弱词命中即算对

**证据**：`zcode_direct_pipeline.mjs:603-604`

```js
const text = [note.primary_finding, ...surviving.map(h => h.name),
              ...surviving.flatMap(h => h.logic_chain ?? [])].join(" ").toLowerCase();
const kwHit = kw => kw.some(k => text.includes(k.toLowerCase()));   // ANY keyword
```

`kwHit` 是 **OR 语义**：命中**任意一个**关键词即判 `top1 = true`。

后果举例（`tep_d11_reactor_cooling_random` 的关键词含 `冷却`、`随机`、`波动`、`cooling`）：
一份**错误**诊断，只要在主结论或任一条逻辑链里出现"冷却"二字，就被判为 Top-1 正确。

再看 `skab_cavitation_13` 的关键词 `["cavitation","气蚀","空化","两相流","汽蚀"]` ——
这组倒是判别性的（负对照测试因此能通过）。
但 `skab_valve1_1` 的 `["valve","inlet","入口","阀","关闭","节流"]` 中，
**"入口"是泵入口描述里的常用词**，容易误命中。

**修复**：改为判别性判据，二选一：
- **全词项要求**（AND）或 **主体词 + 限定词**（(cavitation) OR (两相流 AND 泵)）；
- 或引入**否定集**（命中"排除/eliminated"上下文中的关键词不计分），
  因为 `note.hypotheses` 里 `verdict: "eliminated"` 的假设名同样进入 `text`——
  即：**把"被排除的假设"当成"主结论"计分**。这是一个真实的误判通道。

> ⚠️ 最后一条尤其严重：`text` 只纳入 `surviving` 假设，这点是对的；
> 但 `d11` 的"存在随机波动"这类**弱判别词**仍在 surviving 链里容易擦边命中。

### 🔴 C2（致命，必须改写声明）基准不执行多 agent 管线

**证据**：`scripts/benchmark/run-benchmark.mjs` 的 S3 只做存在性校验：

// S3 diagnose (agent-in-the-loop)
