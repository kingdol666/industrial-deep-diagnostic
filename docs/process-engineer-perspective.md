## Q1. 真实工厂里，看到"转化率下降"，我们实际怎么排查？

### 1.1 操作工的第一反应（前30分钟）

转化率报管亮了，DCS屏上转化率从95%掉到88%。操作工**不会**先想"是不是Arrhenius反常"。他们的排查链是：

```
Step 0: 这是真的吗？仪表有没有问题？
  ├─ 在线分析仪校准气通了吗？标定过期了吗？
  ├─ 取样阀有没有堵？（工艺介质结晶卡阀很常见）
  ├─ DCS点是不是跳了个通讯断线？
  └─ 化验室刚刚出的数据对得上吗？→ 如果不对，先派人工取样

Step 1: 是不是最近有操作变动？
  ├─ 换班了吗？（交接班记录翻一遍）
  ├─ 进料切换了吗？（换储罐、换原料批号）
  ├─ 刚刚做了什么操作？（提负荷、切塔、调配方）
  └─ 环境条件变了吗？（暴雨导致循环水温骤降、气温骤变影响冷却塔）

Step 2: 走到现场看一眼
  ├─ 反应器有没有异响？（催化剂床层塌陷会"咕噜咕噜"）
  ├─ 有没有泄漏？（法兰滴漏、阀门盘根渗）
  ├─ 温度有没有局部热点？（红外枪扫一遍）
  └─ 压力表和DCS对得上吗？（就地仪表 vs 远传）
```

**关键洞察 #1：工厂排查是"否定法"驱动的。** 操作工会先排除"假信号、操作失误、临时扰动"这三类，**之后**才会进入"是不是有真问题"。你们系统的diagnosis.json直接跳到了竞争假设（硫中毒vs烧结vs进料波动），**跳过了操作工脑子里最前面的那三道筛子**。这导致——工程师看到报告会想："你们确认这不是仪表问题或交接班扰动了吗？"

### 1.2 工艺工程师介入后的排查（2-8小时）

操作工30分钟排查无果，上报工艺工程师。我的真实工作流：

```
Step 3: 调趋势图——但不是所有参数一起看
  ├─ 先看"转化率 + 副产物 + 选择性"三个质量指标的趋势（它们应该协同变化）
  │   └─ 如果转化率掉但副产物没动 → 可能是计量/采样问题，不是真反应问题
  │   └─ 如果转化率掉 + 副产物涨 + 选择性掉 → 真的是反应出了问题（三联征）
  ├─ 再看"反应温度 + 压力 + 进料量 + 氢油比"四个关键过程参数
  ├─ 然后看"催化剂活性"有没有替代指标（温度-压力补偿后的k值）
  └─ 最后对比"黄金批次"——历史上质量最好的那段时间，参数是什么样

Step 4: 关联事件——这是工艺工程师的核心技能
  ├─ "转化率什么时候开始掉的？" → 精确到小时
  ├─ "那个时间点前后，原料批次换了吗？" → 查原料检验单
  ├─ "同期其他指标有没有共变？" → 比如冷却负荷、放热量
  └─ "是渐变还是阶跃？" → 渐变=渐进性失效(中毒/结垢)，阶跃=事件(设备故障/换料)

Step 5: 化验室出动——数据系统看不到的东西
  ├─ 原料全分析（硫形态分析——总硫不够，要分噻吩硫/无机硫/有机硫）
  ├─ 催化剂取样（如果可及）——BET比表面、金属分散度、XRD看晶相
  ├─ 产物详细分析——副产物是什么类型？ tells you 反应路径偏了
  └─ 留样备查（出了事要追溯）

Step 6: 决策——继续观察 / 调整 / 停车
  ├─ 趋势还在恶化吗？恶化速率？
  ├─ 影响下游了吗？（产品指标卡边了没有）
  ├─ 有没有安全裕度？（转化率从95掉到70 vs 掉到40，决策完全不同）
  └─ 停车检修的代价 vs 带病运行的代价
```

### 1.3 我们实际需要的信息（系统该补什么）

| 我们脑子里的问号 | 当前系统给的吗 | 缺什么 |
|---|---|---|
| "这是真信号还是仪表问题？" | **没给**。报告直接默认数据真实 | 数据可信度预检：传感器一致性校验、采样代表性评估 |
| "什么时候开始的？是渐变还是阶跃？" | ✅ 变点检测(change_point_detected)有 | 要更明确：渐变斜率 vs 阶跃幅值，对应不同根因类别 |
| "那个时间点发生了什么？" | ⚠️ 有事件标记但不够全 | 事件日志关联：换班、换料、天气、设备动作的统一时间轴 |
| "三联征协同吗？"（转化率+副产+选择性） | ⚠️ 部分有 | 质量指标间的协同性诊断：协同恶化=真反应问题，独立波动=计量问题 |
| "对比黄金批次差多少？" | **没给** | 基线/黄金批次对照：当前参数偏离最优批次多少σ |
| "影响下游了吗？安全裕度还有多少？" | **没给** | 影响传播链 + 裕度耗尽倒计时（"按当前速率，X天后产品不合格"） |

**给设计团队的最重要一句话**：工厂排查是从"现象→时间→事件→物料→设备"的物理因果链逆推的，不是从统计相关性顺推的。你们的报告逻辑是"数据→统计→假说→排除"，这是分析师视角；工厂要的是"现象→时间线→事件关联→可执行的下一步"。**方向是对的，但叙事顺序要倒过来。**

## Q2. diagnosis.json 对工艺工程师够用吗？还缺什么？

### 2.2 够用的部分（说实话，已经超出我的预期）

我看过CSTR和换热器两份报告，**竞争假设排除框架（H1-H4 + 可区分性矩阵 + 排除置信度）这套东西，本质就是我们老师傅脑子里做诊断的过程**，只是我们不会这么结构化地写出来。具体表扬：

- ✅ **排除逻辑而非确认逻辑**——这太对了。工厂里最怕的是"确认偏差"，先有结论再找证据。你们强制生成4个竞争假设，逼着考虑"万一不是A是B呢"，这正是资深工程师的习惯。
- ✅ **物理机制链验证**（链1→链4：噻吩吸附→活性位减少→转化率降→操作工提温补偿）——这条链我看了会点头，因为和我现场经验一致。特别是**区分"提温是原因还是结果"**（操作工补偿），这是新手最常犯的错。
- ✅ **Simpson反转识别**（换热器报告里HTC-cold_inlet跨单元伪相关）——这个发现非常专业。我见过太多工程师拿跨换热器的HTC做对比然后得出错误结论。
- ✅ **事件的自然实验价值**（催化剂再生后活性恢复→确诊；泵维护后HTC不恢复→排除颗粒污垢）——这是利用现场自然扰动做因果识别，非常聪明。

### 2.2 缺的部分（作为工艺工程师，我还想要这些）

#### 缺失 #1：可操作性分级——"我现在该干什么"

诊断报告告诉我"根因是噻吩中毒"，但没告诉我**"这个结论对应的行动等级是什么"**。我需要的是：

| 诊断结论 | 行动等级 | 我的决策 |
|---|---|---|
| 催化剂中毒，活性降至40%，趋势仍在下降 | **URGENT** | 立即安排再生/更换，评估原料 |
| 换热器结垢，HTC下降10%，45天周期 | **SCHEDULE** | 排入下次检修窗口，不紧急 |
| 温度和压力有交互效应 | **INFORM** | 记入工艺知识库，下次DOE用 |

**diagnosis.json缺少一个`action_priority`字段**，把"诊断结论"翻译成"行动紧急程度"。工厂里的一切决策最后都落到：**多急 / 多贵 / 谁批 / 停不停车**。

#### 缺失 #2：物料/能量平衡闭合度

工艺工程师判断"数据可不可信"，第一招是**物料平衡和能量平衡**。进料=出料+反应消耗+损失，放热=冷却带走。你们系统做了大量统计验证（Simpson/去趋势/Granger），但没做最基础的**守恒律校验**：

```
CSTR场景应检查:
  - 进料总量 ≈ 出料总量 + 反应消耗（按转化率算）？
  - 反应放热（按转化率×反应焓）≈ 冷却水带走热量？
  - 如果不闭合 → 数据有缺失或计量有问题 → 所有结论打折
```

换热器场景同理：热侧放热 = 冷侧吸热 + 散热损失。**平衡不闭合的数据，做多少统计验证都是空中楼阁。** 建议在Phase 0数据质量评估加一道"守恒律闭合度"检查，闭合度<95%的数据要明确标注"基于不完全平衡的数据"。

#### 缺失 #3："下一步该采什么样 / 做什么实验"

诊断报告止步于"根因是噻吩中毒"。但工艺工程师拿到这个结论后的**第一反应**是："我要怎么证实？做什么化验？"

你们的报告应该在根因结论后附一个**验证实验清单**：

```
诊断结论: 噻吩中毒（置信度90）
建议验证实验（按成本排序）:
  1. [低成本] 原料噻吩专项分析（GC-SCD，检测限0.01ppm）—— 当前总硫5-8ppm不够
  2. [中成本] 催化剂取样BET+金属分散度—— 活性表面积定量
  3. [高成本] 热氢汽提再生实验—— 再生后恢复度定性中毒可逆性
预期: 如果实验1检出噻吩>0.05ppm → 确认根因
```

这条我**特别强调**——你们的系统定位是"DOE顾问"，但DOE不只是优化实验，**诊断验证实验也是DOE**。系统应该能把"确诊根因"和"验证实验设计"连起来。

#### 缺失 #4：跨班次/跨人员知识传递

工厂的现实：**诊断是A做的，执行是B做的，复盘是C做的**。三班倒、人员流动快。diagnosis.json是给机器读的，但工厂需要的是**一份交接班就能用的"诊断结论卡"**——半页纸，写着：

```
【异常诊断结论卡】2026-07-30 早班→中班交接
异常: CSTR转化率从95%降至88%（72h内）
系统诊断: 噻吩中毒可能性76%，待原料化验确认
当前状态: 趋势仍在下降，速率-0.3%/天
安全裕度: 距产品不合格阈值还有~48h（按当前速率）
行动: 已送样噻吩分析（预计4h出结果）；如确认，安排催化剂再生
注意: 不要继续提温补偿（会加速烧结），改为降负荷维持
```

建议增加一个`shift_handoff_card`输出——不是给DOE专家的，是**给下一班操作工的**。

## Q3. "安全操作窗口"在工厂里意味着什么？

### 3.1 工艺工程师如何理解"185-190°C"

你们safe_operating_windows.json里写"温度安全窗口182-191°C，optimal_range 184-189"。**作为工艺工程师，我看到这个数字，脑子里会立刻追问三个问题：**

**问题1：这个窗口是基于什么定义的"安全"？**

- 如果是"历史数据中质量达标时的参数分布范围"（你们当前的method）——**这只是"历史经验范围"，不是"安全范围"**。我说得更直白：历史没炸过 ≠ 安全。历史在185-191质量达标，只证明"在这个范围内产品质量OK"，**没证明设备安全、没证明没有潜在风险**。
- 工厂里真正的"安全窗口"是**多层嵌套**的：

```
安全窗口的层次（从外到内）:
  ┌─ 设计极限（设备铭牌/MAWP/材料耐受温度）—— 绝对不可逾越
  ├─ 法规/保险限定值（安全规程/环保排放限值）—— 逾越要担责
  ├─ 工艺规程上限（SOP规定的操作区间）—— 逾越要审批
  ├─ 历史经验范围（曾经安全运行过的区间）—— 你们的safe_window停在这里
  └─ 最优操作区间（质量+能耗+收率综合最优）—— DOE要找的
```

**你们目前只给了最里面两层。缺了外面三层。** 特别是设计极限和法规限值——如果系统建议升温到191°C，但设备的设计上限是195°C，工艺工程师会问："191离195只有4度，热惯性+测量误差±2度，这安全吗？"

**问题2：这个窗口考虑了时间维度吗？**

"185-190°C安全"——**是稳态安全还是瞬态安全？** 工厂里的事故往往不是稳态运行出的，是**升温/降温瞬态**出的：

- 升温速率过快 → 热应力 → 设备疲劳
- 温度突变 → 反应失控（放热反应的正反馈）
- 长期高温运行 → 材料蠕变/老化积累

你们的窗口是**静态的快照**。工艺工程师需要的是**动态边界**："从185升到190，允许的升温速率是多少？在190最多停留多久？降温到185需要多少时间避免热冲击？"

**问题3：这个窗口考虑了耦合吗？**

"温度185-190安全"——**是在什么压力、什么进料组成下安全？** 如果压力也变了、进料组成变了，原来安全的温度窗口可能就不安全了。这就是Q4要讲的交互效应。

### 3.2 工艺工程师不会接受的盲区

| 盲区 | 为什么不接受 | 系统该怎么补 |
|---|---|---|
| **外推到历史范围之外** | "历史最高191°C，你建议195°C" → 工艺工程师：我们从没去过195，你凭什么说安全？ | 标注`extrapolation_flag`，外推区间必须标红+附物理模型依据 |
| **没有安全裕度** | "上限191°C"直接当操作目标 → 测量误差±2°C，等于实际可能到193 | `operating_limit` = `safe_max - margin`，margin按传感器精度+工艺波动给定 |
| **忽略了不可逆损伤** | "温度可以到190" → 但190°C下催化剂寿命从12个月降到6个月 | 关联`degradation_rate`：每个参数水平对应的设备/催化剂劣化速率 |
| **没有设备级约束** | "反应温度190OK" → 但下游换热器只能处理到这个热负荷 | 增加`downstream_constraint`链：这个参数动了，下游什么设备受影响 |
| **没区分"稳态"和"开车/停车"** | 窗口只考虑正常运行 → 开车暖管/停车降温的安全窗口完全不同 | 标注`operating_mode`：steady_state / startup / shutdown / load_change |

## Q4. 交互效应在工艺上意味着什么？真实例子

### 4.1 交互效应的工艺本质

统计上说"X1对Y的影响取决于X2的水平"（interaction_coef显著）。**工艺上说，这叫"协同效应"或"拮抗效应"——两个参数不是独立起作用的，而是像一个化学反应里的两个反应物，配比决定了结果。**

我用三个你们验证过的场景讲：

### 4.2 真实例子1：CSTR温度 × 氢分压（协同，但有上限）

```
场景: CSTR催化加氢，目标=转化率
单独看:
  - 温度185→190°C (+5°C): 转化率 +2.1%（Arrhenius加速）
  - 氢压23→26bar (+3bar): 转化率 +3.6%（反应物浓度增加）

交互效应（工艺理解）:
  低温+低压: 转化率85%（动力学慢+反应物少，双重瓶颈）
  高温+高压: 转化率97%（动力学快+反应物足，协同提升）← 升温+升压一起调收益最大
  高温+低压: 转化率89%（动力学快了但反应物不够，氢气成了限制因素）
  低温+高压: 转化率90%（反应物够了但动力学慢，温度成了限制因素）

工艺含义: 
  这就是为什么"只调一个参数"效果差——你提了温度但氢气跟不上，
  多出来的动力学潜能被饿死了。
  DOE启示: 升温和升压必须成比例地调（按化学计量比），单因素实验会严重低估潜力。

危险边界（交互的另一面）:
  高温+高压到了某个临界点 → 反应失控（放热速率>冷却能力）→ 飞温
  这个临界点是交互效应最危险的体现——单独看每个参数都在"安全窗口"，
  但组合起来触发了系统级风险。你们的interaction_effects.json必须标注这个!
```

### 4.3 真实例子2：BOPET多区温度交互（空间耦合）

```
场景: BOPET薄膜挤出，39列里有多区加热（zone1-zone8温度）
质量目标: 厚度均匀性 + 结晶度 + 光学性能

交互效应（工艺理解）:
  zone1（挤出段）温度 × zone5（计量段）温度:
  
  zone1偏低 + zone5正常: 熔融不充分 → 后续怎么加热都有凝胶点 → 厚度不均
  zone1正常 + zone5偏高: 熔体过热 → 降解 → 黄度上升
  zone1正常 + zone5正常: 黄金组合
  
工艺含义:
  挤出是"串联工艺"——前一区的输出是后一区的输入。
  前区没做好，后区救不回来。这叫"串联约束"。
  DOE启示: 多区温度不能独立优化，必须做"温度曲线优化"而非"单点优化"。
           你们的关系图谱必须体现这种空间串联结构（zone1→zone2→...的因果序）。
```

### 4.4 真实例子3：换热器流量 × 入口温度（隐藏交互）

```
场景: 管壳式换热器结垢诊断
交互效应:
  流量 × 冷却水入口温度 → 对结垢速率的影响
  
  低流量 + 高入口温: 管壁温度高 → CaCO3溶解度低 → 结垢加速（双重恶化）
  高流量 + 低入口温: 管壁温度低 → 结垢慢（双重保护）
  低流量 + 低入口温: 入口低但流速低→换热差→管壁温度实际不低 → 结垢中等
  
工艺含义:
  "提流量"和"降入口温度"都是抗结垢手段，但两者有交互——
  高流量本身会增加湍流冲刷（减少垢层），同时降低管壁温度（减少析出）。
  但高流量也增加泵功耗（你们报告里泵功耗增2.8倍）。
  DOE启示: 抗结垢优化是多目标（结垢速率 vs 能耗），交互效应决定了最优配比。
```

### 4.5 对系统的建议

你们的`interaction_effects.json`设计了interaction_coef和p_value——**统计上够了，但工艺上不够**。每个显著交互必须附带：

1. **工艺解释**：为什么有交互？（物理机制，不能只给统计数字）
2. **交互类型**：协同(synergistic, 正交互) / 拮抗(antagonistic, 负交互) / 串联(sequential, 前区依赖)
3. **临界点/拐点**：交互在什么参数水平下发生质变？（如温度×压力的失控临界）
4. **安全含义**：这个交互是否意味着"单独安全但组合危险"？（这是工厂最怕的）

## Q5. 如果系统建议"升温3°C+升压1.5bar"，工艺工程师会担心什么？

### 5.1 我的真实心理活动（作为车间主任）

系统弹出建议："升温3°C（185→188）+升压1.5bar（24→25.5），预期转化率+4.2%"。

**我的第一反应不是"太好了"，而是"凭什么让我信你"。** 然后脑子里跑过这一串：

```
担心1: 安全——这会不会炸？
  ├─ 反应器MAWP（最大允许工作压力）是多少？25.5bar离它多远？
  ├─ 188°C是放热反应，升温会不会触发失控？失控的临界温度是多少？
  ├─ 安全联锁（SIS）在什么压力/温度触发？我会不会触发停车？
  └─ 升温升压同时进行——瞬态叠加负荷，冷却系统能扛住吗？

担心2: 设备——这会不会损坏设备？
  ├─ 188°C对催化剂寿命的影响？（可能加速烧结，从12个月→8个月）
  ├─ 25.5bar对密封件的压力？（法兰垫片、机械密封额定值）
  ├─ 长期运行疲劳累积——这周调了，下周还能再调吗？
  └─ 下游设备能处理这个工况吗？（压缩机、分离罐、换热器）

担心3: 质量——这会不会反而搞砸质量？
  ├─ 转化率+4.2%，但副产物呢？选择性呢？（交互效应！）
  ├─ 升温可能让副反应也加速——主反应+4.2%，副反应+8%？
  ├─ 产品规格还有多少裕度？万一偏了怎么办？
  └─ 有没有历史数据支撑这个区间？（外推到了历史范围外吗？）

担心4: 成本——这笔账划算吗？
  ├─ 升温3°C要多烧多少燃料/蒸汽？
  ├─ 升压1.5bar压缩机要多耗多少电？
  ├─ 转化率+4.2%能多产多少产品？收益覆盖成本吗？
  └─ 催化剂寿命缩短的折旧成本算进去了吗？

担心5: 合规——这要不要审批？
  ├─ 这算不算"变更"（MOC/Management of Change）？要不要走流程？
  ├─ 升温超过工艺规程上限了吗？超了要谁签字？
  ├─ 环保排放会变吗？（温度高了VOC排放可能增加）
  └─ 保险/HSE知不知道我们在改工况？

担心6: 执行——谁来干？什么时候干？
  ├─ 现在是高峰负荷，能不能调？（产线满负荷时不动参数是铁律）
  ├─ 夜班能不能做？（高风险操作不在夜班做——人少、反应慢）
  ├─ 操作工会不会抗拒？（"我这么跑了三年没出事，你让我改？"）
  └─ 调完怎么验证效果？多久看一次？调坏了怎么回退？
```

在上述担心被回答之前，**我不会执行任何参数调整建议**。我需要系统提供：

## Q6. 数据诊断系统的最佳定位：离线顾问 vs 在线辅助？

### 6.1 我的明确建议：分三阶段，不要一步到位

| 阶段 | 定位 | 部署约束 | 何时进入下一阶段 |
|---|---|---|---|
| **Phase 0（当前）** | 离线事件分析顾问 | 工程师手动导数据→系统分析→出报告 | 3个场景报告被工厂采纳且验证准确 |
| **Phase 1（6-12月）** | 定期巡检顾问（每日/每周批处理） | 自动拉DCS数据→定时分析→异常预警推送 | 工厂建立对预警的信任后 |
| **Phase 2（12-24月）** | 在线只读辅助（实时推荐，不闭环控制） | DCS旁路只读接入→实时计算→操作屏推荐 | 经过功能安全评估+网络安全认证 |
| **Phase 3（远期）** | 闭环优化（慎之又慎） | 需SIL认证+冗余+人工监督 | ——多数工厂永远不走到这一步 |

### 6.2 离线顾问（当前定位）的部署约束

```
✅ 优势:
  - 无延迟要求，可以用重型ML（你们的SHAP/partial_corr都能跑）
  - 无安全风险（不直接控制设备）
  - 不需要网络安全认证/功能安全认证
  - 出错了最多是报告不准，不会造成事故
  - 工程师有时间review，建立信任

⚠️ 约束:
  - 数据时效性差（导出的数据可能滞后数小时-数天）
  - 依赖工程师主动使用（不用就等于没有）
  - 无法捕捉瞬态异常（导出时刻已过）
  - 报告太长太专业，操作工看不懂 → 需要分层的报告（给操作工的1页卡 vs 给工程师的完整报告）

📌 部署要点:
  1. 报告分层: 执行摘要（厂长）→ 行动卡（操作工）→ 技术报告（工程师）→ 数据附录（分析师）
  2. 接入方式: 支持手动上传CSV + 定时从PI/PHD历史库自动拉取
  3. 结果落地: 报告要能导出为"工艺改进通知单"走工厂OA审批流程
  4. 知识积累: 每次诊断的结果要入库，形成"本厂工艺问题案例库"
```

### 6.3 在线辅助（未来）的部署约束——这才是真正的挑战

```
🔴 核心约束:
  1. 延迟: 推荐必须在5秒内出（操作工不会等30秒看分析）
     → 当前管线跑一次要几分钟（统计+VLM+诊断），必须做实时轻量化版
  2. 可靠性: 7×24不能宕机，要有热备
     → 当前是"跑一次出报告"，在线要改成"持续运行的服务"
  3. 安全: 绝对不能误触发设备动作
     → 只读推荐模式: "建议升温3°C"显示在屏上，由操作工确认后手动执行
     → 严禁直接写DCS设定值（除非经过SIL2/SIL3认证）
  4. 网络安全: 接入DCS需要经过防火墙/单向网闸
     → 工厂的OT网络是隔离的，你们系统要在DMZ区部署
  5. 报警管理: 不能制造"报警疲劳"
     → 你们的异常检测要设阈值，一天推送不超过3-5条
     → 每条必须有明确的"为什么+该怎么做"

🚫 绝对红线（在线辅助阶段不可逾越）:
  - 禁止直接控制任何执行机构（阀门/泵/加热器）
  - 禁止绕过安全联锁（SIS）做任何推荐
  - 禁止在未告知操作工的情况下修改DCS设定值
  - 禁止推荐超出工艺规程范围的参数（除非有MOC审批记录）
```

### 6.4 我的最终定位建议

**这个系统在工厂里的最佳身份是"工艺工程师的超级助手"，不是"取代工艺工程师的AI"。**

具体地说：
- 它**不应该**自动调参数、自动决策、自动执行——那是操作工和工程师的职责，也是法规要求。
- 它**应该**做工艺工程师没时间做的事：同时盯100个参数的趋势、发现人眼看不出的微妙关联、把老师傅脑子里的经验结构化成可查询的知识库、在海量历史数据里找到最优工况区间。
- 它的最大价值不是"代替人判断"，而是**"让人判断得更快更准"**——把"3天才能排查清楚的异常"压缩到"3小时"，把"凭经验猜的参数调整"变成"有数据支撑的建议"。

**最后一句**：工厂里最值钱的不是数据，不是算法，是**"出了事有人担责"**。系统的每一条建议，最终都由一个有名字的人签字执行。所以系统的输出必须是**"可审计、可追溯、可解释"**的——不是黑箱给个数字就完了，而是每一步推理都有据可查、每个建议都有证据等级、每次调整都有记录可回溯。**你们现在的竞争假设框架+证据等级标注，方向完全正确——继续往"可审计性"方向强化，而不是往"自动化"方向走。**
