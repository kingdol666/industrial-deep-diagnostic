## 二次评审：生产化可行性 + 非设备数据适用性（同日续）

用户追问：能否真正投入生产/企业数据应用；除根因诊断外的其他流程设计是否优秀；非设备数据（生产管理、人员管理）能否用同一逻辑分析出报告。

- `docs/plan-digital-worker-idd-2026-10-01.md`（定位 = 只做分析引擎；自列 P1/P2 缺口）

关键结论（供复用）：
- **生产化**：技术可跑（Docker/nginx/鉴权/健康检查/CLI），但**企业级缺口 5 项且系统自认**：多租户与数据隔离（diagnostic_runs 无 user_id/tenant_id，listRuns 全局可见）、全局并发/优先级队列、RBAC 授权（users.role 字段存在但无执行）、高可用（SQLite 单机）、外部 LLM 依赖韧性。→ 定位应为「可部署的单机分析服务 / 大平台的分析引擎」，非「多租户企业平台」。
- **其他流程设计优秀**：共同范式 = 确定性脚本算数 + agent 只解读 + 门禁裁决 + 诚实降级（not_estimable/not_assessable 是合法结果）。sentinel / stability-report / doe-analyzer / tuning-memory / optimizer-loop 均属高水准工程纪律。
- **数据适用性三档**：① 强项 = 数值时序 + 有物理/工艺机制（设备、能耗、环境、实验室、DOE）；② 有条件 = 数值时序但机制需从「物理」改写为「业务」（排产/OEE/库存/质量成本），统计层可复用、本体层需扩展；③ 不适用 = 事件/类别/关系型数据（考勤/绩效/离职/招聘）——推理内核四条件中的「物理机制」无控制方程可依，永不闭环。
- **关键洞察**：护城河恰是约束本身。为做人员数据而放弃「四条件因果」= 退化为普通统计工具，反失价值。若扩展非设备域，应保留统计内核（反伪相关套件）作通用层、把 physical_meaning 抽象为 mechanism、新增独立业务 skill，不污染工业管线。
- 证据：grep 全 skills 无任何 HR/人员/业务分析 skill；timestamp 出现在 114 个 skill、时间列 26、Δt 23、时序 21 → 时序依赖极深。
