Why This System Exists

工业诊断的核心挑战

质量异常发生时，工程师面临的是三个互相孤立的困境——这也是这套系统诞生的原点。

📈 数据孤岛
传感器数据、工艺参数、质检记录分属不同系统。工程师需要手工导出、对齐、交叉分析——这个过程可能花掉一整天。
缺少统一的数据视图
📚 知识孤岛
工艺经验=老师傅的直觉。SOP和手册"存在那里但没人读得及"。诊断结论依赖个人的经验运气，无法系统化。
领域知识被固化在个体经验中
⚙ 机理孤岛
统计相关≠物理因果。很多诊断系统找到相关就交差，但工程师真正需要的是——哪个参数改变导致了什么问题，以及背后的物理原因。
统计信号需要物理验证
⚠️ 结果孤岛
诊断结果难以审计。"你凭什么说这个问题是A原因？"——没有证据链、没有置信度标注、没有备选假设分析。
结论不可追溯不可验证
Solution

三重知识融合定位

系统的独特之处在于三个知识源必须协同工作——任何一个单独使用都会产生不可靠的诊断。

①
数据自描述
列名模式、数值范围、统计特征揭示工艺类型。系统不做预设——从数据中发现场景。
输入 → 特征感知
②
RAG 领域知识
从工艺手册、SOP、论文中检索物理原理与失效模式。知识被"理解"而非机械复制。
检索 → 深度理解
③
第一性原理物理
每个统计相关必须追溯到控制方程。面对未知参数——从守恒律和量纲分析推导。
相关 → 因果验证
⚙ 双视角输出 — 每条诊断结论的两个必要视图
纯工艺波动诊断：从过程数据识别异常漂移、失稳、阈值行为 · 工艺+检测双驱动诊断：过程异常是否确实进入了缺陷因果链
I
Design Philosophy

设计哲学

诊断是排除，不是确认 · 四个条件缺一不可 · 竞争假设驱动

整套系统的底层逻辑：如何思考一个问题，比用什么工具解决更重要

First Principle

诊断是排除，不是确认

每个结论必须同时通过四道验证。缺失任意一项，自动标记为 [HYPOTHESIS]——不进入最终结论。

⏰ ① 时间先后
潜在原因必须发生在效果之前。用时间戳或变化点确认序列。
反模式：相关≠因果，忽略时序
⚙ ② 统计显著
相关性/差异经统计验证——含分层分析排除混杂因子。
反模式：聚合相关可能被子组分逆转
⚙ ③ 物理机制
存在可追溯的控制方程或守恒律解释。不支持则无效。
反模式：STATISTICAL_ONLY ≠ 根因
✓ ④ 无矛盾
不与已知事实和物理约束冲突。否定证据直接排除假设。
反模式：选择性呈现支持性数据
结论类型：DETERMINEDCOMPETING_SETNEEDS_DATA
Four Pillars

支撑跨行业的四大设计支柱

系统的核心不是针对某个行业的模板，而是四个能够适应任意工业场景的通用设计原则。

① 场景自适应 Scenario-Adaptive
从数据特征出发——列名、值域、统计模式自动决定分析策略。没有一个固定分类树，只有持续适配的分析路径。
反模式：对CNC数据硬套"CNC模板"于非CNC场景
② RAG深度理解 Deep Understanding
RAG知识被"读懂"而非机械复制。语义理解后与数据结构化对齐——提取物理原理与因果链路。
反模式：逐字段从RAG输出复制到本体
③ 数据⇆本体双向 Bidirectional
本体预测→数据验证；数据揭示→本体解释。差异本身就是诊断信号——不匹配的地方往往藏着根因。
反模式：独立建本体和分析数据，不做交叉验证
④ 物理驱动推理 Physics-Based
每个统计相关必须追溯到控制方程。第一性原理推导超越已知故障库的局限。
反模式：「参数X与质量相关，因此X是原因」
Competing Hypotheses Protocol

竞争性假设协议

假设生成 → 数据区分性评估 → 排除 → 结论。每一步都记录了为什么保留或排除某个原因。

✓
DETERMINED
单一假设排除所有竞争项。四个条件全部满足，证据充分。
置信度上限：85
⚠
COMPETING_SET
多个假设在现有数据中不可区分。明确标注无法排除的选项。
置信度上限：65
🔎
NEEDS_DATA
现有数据不足以判定。指明需要哪些额外数据。
等待新数据
反推测四条件： 时间先后 → 统计显著 → 物理机制 → 无矛盾   |   结论受限最弱证据等级   |   每个假设需具 falsification_conditions

Steps 0 → 3

数据到知识：前半程管线

从原始数据文件到结构化领域知识的转化过程——这是诊断的基础设施建设。

⚙ Step 0-1: 初始化与勘探
  • setup.mjs 创建运行目录 + .pipeline_events.jsonl 执行证明
  • inspect.mjs 流式解析 CSV/JSON/TSV（超大文件友好）
  • 产出：input_manifest.json + user_context.json
  • 三种交互模式：auto / interactive / minimal
📖 Step 2: 领域本体（context-builder）
  • RAG检索 + R1-R4深度理解协议：语义理解→知识对齐→物理提取→差距识别
  • 产出：ontology.json + schema.json + extracted_knowledge.json
  • 支持ChromaDB向量检索 + 本地回退
📈 Step 3: 数据分析（data-processor）
  • 高级统计引擎：Pearson/Spearman/分层/去趋势/变点/延迟CCF
  • Simpson's Paradox 检测 + 趋势混淆分析
  • 场景自适应可视化 + VLM视觉分析委托
  • 强制交接文件：data_analysis_conclusion.json → diagnostician
👁 Step 3.5 VLM视觉分析（内部委托）
  • 由data-processor在Phase 5.5内部委托vlm-visual-analyzer
  • 先读ontology理解参数含义 → 再带知识看图
  • 产出：visual_analysis.json + image_captions.json
  • 本体感知的图+统计+知识联合提取
预热并行：本体未就绪前 data-processor 可先做基线分析
Steps 4 → 8

诊断到交付：后半程管线

从竞争性假设推理到最终报告交付——这是系统的价值生成阶段。

🧠 Step 4: Diagnostician（核心引擎）
  • Phase 0-7 内部流程：数据探测→假设生成→区分性评估→排除→判定→置信度校准
  • 融合数据 + 本体 + 物理 + VLM 四类证据
  • 每个结论含：ontology_data_physics_proof + physical_logic_chain + falsification_conditions
  • 产出：diagnosis.json evidence.json confidence.json reasoning_chain.json（×4 Schema验证）
⚙ Step 5-5b: 质量门预审（并行关卡）
  • Judge：10项评分 + 物理源审计。Verdict: pass(≥90) / needs_repair / major_issues / fail
  • Pre-audit：report-reviewer在PRE_REPORT_AUDIT模式下并行审计物理表述
  • 硬门：blocking_issues=0 + score≥90 才允许进入报告生成
📝 Step 6-7: 报告与审计
  • Reporter：生成791+行/20节中文诊断报告 + run_summary.json
  • Report-reviewer：独立物理真实审计 → optimizer.md
  • ENDORSED → 交付 | CONDITIONAL/REJECTED → 修复循环
⚙ Step 8: 最终校验交付
  • finalize-run-artifacts.mjs → 刷新证据闭合报告 + 记录run_completed
  • artifact-check.mjs → 最终门禁验证
  • 校验执行证明、证据闭合、VLM执行记录、诊断质量契约
  • 任何门禁未通过 → 标记为blocked run而非完成

Quality Gates

双重质量保障：Judge + 独立审计

两个独立的审查关卡并行执行，从不同角度确保诊断质量。

⚙ Judge：10项质量门审查
  • 评分覆盖：问题定义完整性、假设充分性、证据支撑、物理推理、反推测检查、置信度校准、过claim控制、推理链审计、阻断问题检查
  • Hard pass不变量：overall_score ≥ 90 + blocking_issues.length === 0 + 推理链无问题
  • judge-gate-check.mjs 门禁：未通过则 reporter 不合法
🔍 独立物理审计（report-reviewer）
  • 预审计模式：Step 5b在PRE_REPORT_AUDIT=true下并行运行，产出optimizer_preflight.md
  • 正式审计：Step 7独立验证所有物理表述，不依赖reporter推导过程
  • ENDORSED → 交付  |  CONDITIONAL / REJECTED → 修复
  • optimizer.md包含：场景优化计划 + 问题 + 验证方案 + 动作分类
报告门禁：Judge未pass → reporter不能启动 审计门禁：审计未通过 → 自动修复循环
Engineering Contract

三层工程契约保障

除了算法和逻辑之外，工程实现层面还有三层契约确保系统可靠运行。

📋
Schema-First 写入协议
写入任何结构化文件前必须读取对应Schema：先读→构造→一次写入→立即验证。失败则检查字段定义后重写，防止token浪费。
所有结构文件均受此约束
📜
执行证明日志
.pipeline_events.jsonl记录每个步骤的开始/完成/依赖等待/修复事件。仅产出文件但日志不完整→判定为执行完整性失败。
日志即证据
📐
证据闭合检查
每个诊断结论必须闭合到数据源头：过程异常入口→双驱动入口→本体/物理解释→诊断输出→审查/报告交接。evidence_closure_report.json为机器可读证明。
从数据到结论可追溯
工程交付契约：run_config标准化 + 强制子Agent交付物 + 当前步骤完整性 + 最终门禁  |  不满足则标记为不可交付
