What It Does

把数据转化为可执行的诊断

工业深度诊断系统是一个 场景自适应 的诊断引擎——无需预设工艺类型，从数据特征出发结合三重知识源完成推理。

①
数据自描述
列名模式、数值范围、统计特征揭示工艺类型。无需匹配固定分类树。
②
RAG 领域知识
从工艺手册、SOP、论文中检索物理原理、因果机制与已知失效模式。
③
第一性原理物理
每个统计相关性必须追溯到控制方程；未知参数从守恒律和量纲分析导出。
⚙ 双观点输出 纯工艺波动诊断 工艺+检测双驱动诊断
Core Principle

诊断是排除，不是确认

每个结论必须同时满足四个条件，缺一不可——缺失任一即标为 [HYPOTHESIS]。

⏰ 时间先后
潜在原因必须发生在效果之前。用时间戳或变化点定位序列。
反模式：相关≠因果，忽略了时间顺序
⚙ 统计显著
相关性/差异必须经统计验证（含分层分析排除混杂）。
反模式：聚合相关可能被子组分逆转（Simpson's Paradox）
⚙ 物理机制
必须存在可追溯的控制方程、守恒律或物性关系解释相关性。
反模式：STATISTICAL_ONLY ≠ 根因
✓ 无矛盾
与其他已知事实和物理约束不冲突。否定的证据直接排除假设。
反模式：忽略反证据，仅选择性呈现支持性数据
结论类型：DETERMINED / COMPETING_SET / NEEDS_DATA
Four Pillars

支撑跨行业诊断的四大原则

这套引擎的核心不是模板匹配，而是 数据特征驱动 + 物理约束验证。

① 场景自适应 Scenario-Adaptive
分析始终从数据特征出发——没有硬编码的工艺类型。列名、值域、统计特征决定了如何分析。
反模式：对 CNC 数据硬套 "CNC 模板" 于非 CNC 场景
② RAG 深度理解 RAG Deep Understanding
RAG 知识被语义理解而非机械映射。领域知识被"读懂"后与数据结构化对齐。
反模式：逐字段从 RAG 输出复制到本体
③ 数据⇔本体双向 Data⇆Ontology
本体预测→数据验证；数据揭示→本体解释；差异本身就是诊断信号。
反模式：独立构建本体和分析数据，不做交叉验证
④ 物理驱动推理 Physics-Based Inference
所有相关性必须追溯到控制方程。第一性原理推导超越已知故障模式库。
反模式：「参数X与质量相关，因此X是原因」

搭建运行环境、创建目录结构、流式解析数据文件、感知数据特征。

  • 启动 run_manifest.json & .pipeline_events.jsonl 执行证明
  • uv_env_setup.mjs 自动装 Python 虚拟环境
  • 交互模式：auto interactive minimal
⚙ Step 1: Inspect
  • inspect.mjs 流式解析 CSV / JSON / TSV（超大文件友好）
  • 生成 input_manifest.json: 列名、类型、统计概览
  • 生成 user_context.json: 用户目标、质量定义、已知约束
  • 工艺无关描述：趋势/周期/阶跃/平稳分类 + 时间列检测
产出：00_input/input_manifest.json · 00_input/user_context.json · 00_input/run_config.json
Step 2 · context-builder

领域本体构建 Sub-Agent (Sonnet)

RAG 检索 + 网络搜索 + 本体构建 + 深度物理映射 — 子智能体完全自主执行协议。

📖 R1-R4 深度理解协议

  • R2 知识-数据对齐：将RAG知识与实际列名/量纲对应
  • R3 物理提取：提取控制方程、因果链路、故障模式
  • R4 差距识别：标记数据中存在但未覆盖的域

  • 01_ontology/schema.json — 列-物理量映射
  • 00_input/extracted_knowledge.json — RAG提取知识
  • rag_deep_understanding.json — 深度理解产物
  • clarification_needed.json — 澄清门输入
  • RAG 回退：ChromaDB 不可用时完全本地构建

Step 3 · data-processor

数据处理与可视化 Sub-Agent (Sonnet)

⚙ 高级统计引擎

  • 趋势混淆检测 & 去趋势后残差r
  • 变点检测（CUSUM/贝叶斯）+ 延迟CCF
  • 多重检验校正 & 鲁棒性验证
📊 核心产出
  • 02_processed/ 清洗/验证/异常报告
  • 03_figures/*.png 场景自适应可视化
  • plot_manifest.json + visual_analysis.json
  • data_analysis_conclusion.json — 强制交接文件 → diagnostician
👁 Step 3.5 VLM 视觉分析 vlm-visual-analyzer (Haiku)
由 data-processor 在 Phase 5.5 内部委托。先读 ontology 理解参数物理含义，再带有知识地看 PNG 图表。 本体感知的 VLM 图像分析——图 + 统计 + 知识联合提取结构化视觉证据。

Step 4 · diagnostician

竞争性假设诊断 Sub-Agent (Sonnet)

融合数据、本体、物理机制和 VLM 视觉证据，执行物理约束的根因推理。

⚙ 推理流程（Phase 0-7）
  • Phase 1: Data Probing — 数据特征再验证
  • Phase 2: 竞争性假设生成 — 至少3个物理可区分假设
  • Phase 3: 数据区分性评估 — 每个假设的预期可观测信号
  • Phase 4-5: 排除与判定
  • Phase 6: 置信度校准 + 反推测检查
📜 结构化产出（×4）
  • diagnosis.json — 结论 + 假说排名 + Schema验证
  • evidence.json — 每个证据等级标注
  • confidence.json — 置信度 + 调整日志
  • reasoning_chain.json — R1-R8推理链
  • 每个结论含 falsification_conditions
纯工艺波动诊断 工艺+检测双驱动诊断 必须输出：两种互补推理视图
Methodology

竞争性假设协议

假设→数据区分性评估→排除→结论。当数据无法区分时输出 COMPETING_SET，而非猜一个。

DETERMINED
单一假设排除所有竞争项。所有4个反推测条件满足，证据充分。
置信度上限：85（有严格限制）
COMPETING_SET
多个假设在现有数据中不可区分。必须明确标注 INDISTINGUISHABLE。
置信度上限：65（受严格上限约束）
NEEDS_DATA
现有数据不足以判定。需要额外测量/实验数据才能进展。
置信度：不适用 — 等待数据
⚠ 反推测四大条件
时间先后 → 统计显著 → 物理机制 → 无矛盾 结论受限最弱证据等级

Step 5 · judge

质量门审查 Sub-Agent (Sonnet)

10 项评分标准 + 物理源审计，确保诊断可靠后方可生成报告。

⚙ Verdict 逻辑
pass ≥90 needs_repair 70-89 major_issues 50-69 fail <50
blocking_issues.length=0 是 pass 的必要条件
⚙ 产出与硬门
  • 05_review/judge_feedback.json — Schema验证
  • judge-gate-check.mjs — 硬门，不通过则禁止 reporter
  • Hard pass 不变量：score≥90 + 无 blocking + reasoning chain 无问题
⚙ Step 5b: 预报告物理审计 (并行)
report-reviewer 在 PRE_REPORT_AUDIT=true 模式下并行运行，产出 optimizer_preflight.md。在 Step 6 之前必须确保无 blocking 物理问题。
Step 6 & 7

报告生成与物理审计 Reporter & Report-Reviewer

从结构化诊断产物生成专业报告，再由独立的物理真实审计检查每一个结论。

📝 Step 6: Reporter
  • 产出 report.md — 791+ 行，20 节中文诊断报告
  • 以 visual_analysis.json 为主要图表证据源
  • 同时生成 run_summary.json（Schema验证）
  • Judge 门禁：必须先通过 Judge gate，否则 reporter 启动非法
🔍 Step 7: Report-Reviewer
  • 独立物理真实审计，不依赖 reporter 的推导过程
  • 产出 optimizer.md — 场景优化计划 + 问题 + 验证方案
  • ENDORSED → 完成 | CONDITIONAL / REJECTED → 修复
  • 包含：即时处理 / 低风险优化 / 受控实验 / 测量改进 / 延期处理
Step 8: Present — finalize-run-artifacts.mjs + artifact-check.mjs 最终校验
