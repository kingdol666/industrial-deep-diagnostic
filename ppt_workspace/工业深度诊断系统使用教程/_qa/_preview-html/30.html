第 12 章 · 排错速查：三个等级，按顺序查
九成问题落在这三类里；先看现象，再按顺序做检查，不用猜
先查 L1，再查 L2
L1 · 起不来
服务根本没跑
现象：访问 5180 打不开，或 ind-diag status 里某一行不是 running。

① 端口被占用：查 3210 / 5180 / 8764 三个端口，杀掉占用的进程再启动。

② 命令不返回、报 Service manager timeout：几乎一定是漏了 --detach，服务其实已经起来。

③ RAG 起不来：先确认 Python ≥ 3.10，再切镜像源重跑 uv sync，日志看 .runtime/rag.log。
先看日志再动手：三个日志文件都在 .runtime/ 下
L2 · 跑不起来
服务活着，诊断发不出去
现象：点了开始诊断没反应，或立刻失败。

① 引擎未登录：跑 claude --version / omp --version 确认 CLI 可用；缺 Key 就补 .env。

② 返回 400 HARNESS_UNKNOWN：引擎名拼错了，前端下拉里选。

③ 返回 409 HARNESS_UNAVAILABLE：引擎没装，换一个已就绪的，或先装 CLI。
先拿 Mock 引擎跑一遍，能通说明是引擎问题不是系统问题
L3 · 结果不对
跑完了但结论奇怪
现象：结论不合理、评分低、或反复重跑。

① 先读结论列：COMPETING_SET 不代表失败，它是在告诉你数据不足以区分假设，页面上会列出「最小判别数据集」。

② 检查问题栏写清楚没有 —— 泛泛的问题只会得到泛泛的结论。

③ 查 .pipeline_events.jsonl 确认是否真的执行完；没跑完的运行不算证据。
不确定是否正常？去引擎运行页看产物覆盖是否齐全
三张卡已按「先看现象 → 再定位」的顺序排好
