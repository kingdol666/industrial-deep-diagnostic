# 场景运行说明（拿到数据后怎么跑）

> 本说明用本模板包自带的 BOPET-L3 样例数据演示**三种运行方式**。真实数据到手后把路径换成你们的文件夹即可，
> 其余流程完全一致。

---

## 0. 前置条件

- 仓库根目录：`industrial-deep-diagnostic`（下称 `$ROOT`）
- 后端 3210 / 前端 5180：`ind-diag all`（或在 `$ROOT` 执行 `npm run dev`，见 README）
- Python 环境（脚本工具链用）：`node .claude/shared/scripts/uv_env_setup.mjs`
- 准备好数据文件夹：**本模板的 `02_data/`**，或产线按《数据导出规范》导出的文件夹

---

## 1. 方式 A：Web 控制台（推荐，最省事）

1. 启动服务：`ind-diag all`
2. 把数据文件夹**整体复制**到 `$ROOT/data/` 下并改成有意义的名字：
   ```
   $ROOT/data/L3_GP12_20260920-20261010/       ← 内容 = 本模板 02_data 里的文件（顶层，不要再套一层）
   ```
   （也可用控制台"数据"页的上传功能：单文件 ≤500MB、单次 ≤50 个文件；上传后会落在 `data/.uploads/`）
3. 打开 <http://localhost:5180> → **数据**页确认能看到该文件夹
4. **诊断**页：
   - 分析目标选 **文件夹**（多选文件也可以；选文件夹时系统会自己挑主表并合并同轴表）
   - 引擎（harness）任选，例如 `claude`（`mock` 只用于快速自检，不做真实分析）
   - 分析意图选 **deep-diagnosis**（完整九步管线）；场景名建议填 `BOPET_L3_优品率下滑`
   - 用户问题建议直接粘贴《异常现象与已做排查.md》第四节"我们的问题"
5. 点"开始诊断"，右侧实时看进展；结束后在**报告**页打开 `report.md` 与 `diagnostic-report.html`

> 控制台会把运行产物写到 `$ROOT/workspace/diagnostic-runs/<时间戳>_<场景名>/`。

---

## 2. 方式 B：命令行（把数据交给主 Agent 驱动管线）

在支持该仓库 skill 的 Agent（Claude Code / OMP / ZCode 等）里，直接说：

> 对 `workspace/bopet-data-template/02_data` 做工业深度诊断：
> 目标是定位"优品率下滑 + 横向厚度不匀率上升"的主导原因，
> 使用 skill `industrial-analysis-auto`，按 Step 0–9 全流程执行。

主 Agent 会依次：建运行目录 → E-1 预处理（把文件夹归一成 `00_input/preprocessed_data.csv`，把说明文档放进 `00_input/context/`）→ inspect → 本体 → 数据分析 → 诊断 → 评审 → 报告 → HTML。

**运行配置**：把 `04_运行说明/run_config.sample.json` 复制成运行目录的 `00_input/run_config.json`，
按下表改关键字段（不改也能跑，系统会用默认值）：

| 字段 | 含义 | 本例建议 |
|---|---|---|
| `data_path` | 数据入口：**文件夹**（推荐）或单个文件 | `workspace/bopet-data-template/02_data`（相对仓库根目录解析） |
| `scene_name` | 场景名（进入运行目录名与报告标题） | `BOPET_L3_优品率下滑` |
| `process_description` | 工艺一句话描述 | 见样例文件 |
| `user_objective` | 你的问题（越具体越好） | 见样例文件 |
| `known_faults` | 你怀疑的方向（可空；**只写"怀疑"，不写结论**） | `["原料批次/回料比例变更", "TDO 热风系统", "环境降温"]` |
| `reference_dir` | 参考文档目录（映射表、本体、说明） | `workspace/bopet-data-template/03_映射文档` |
| `ontology.mode` | `auto`（默认，自动构建）/ `full`（强制重建）/ `reuse`（复用已有） | `auto` |
| `interaction_mode` | `auto`（不问问题，直接跑完）/ `interactive` / `minimal` | `auto` |
| `analysis_constraints.time_range` | 只分析窗口内数据 | 可空 |
| `analysis_constraints.focus_signals` | 重点关注的列（可选） | 可空（默认全列） |

**使用预构建本体（可选）**：`03_映射文档/L3_bopet_ontology.json` 已通过 `ontology_schema.json` 校验，
含 61 个参数定义、14 条因果关系、4 条已知混杂因素。两种用法：

- 轻量：让系统自己构建本体，把 `reference_dir` 指向 `03_映射文档`（映射表与本体作为参考被读取）；
- 直接落位：在运行目录里用该文件替换 `01_ontology/ontology.json`（跳过本体构建步骤；需自行确认后续步骤仍按顺序记录事件）。

**单文件运行**：`data_path` 直接指向某一个 CSV（如 `.../02_data/L3_line_main_10min.csv`）也可以，
此时**不会**带入化验表与说明文档（它们不在同一入口），结论会弱一些 —— 推荐用文件夹方式。

## 3. 方式 C：只做数据体检（不跑完整诊断）

拿到产线数据后，先花 1 分钟做格式体检，避免白跑一次完整管线：

```bash
cd $ROOT

# 1) 单表体检：行数、列类型、时间列是否被识别
node .claude/skills/industrial-analysis-auto/scripts/inspect.mjs \
  "workspace/bopet-data-template/02_data/L3_line_main_10min.csv"

# 2) 文件夹体检：主表选择、合并结果、说明文档是否被保留、被排除的表及原因
uv run --project .claude/shared/scripts python \
  .claude/skills/industrial-data-preprocessor/scripts/data_preprocessor.py \
  --data-path "workspace/bopet-data-template/02_data" \
  --output "/tmp/pp_check" --name check
# 看 /tmp/pp_check/preprocessing_report.json：
#   selected_table      ← 被选为主表的文件
#   merge / merge_exclusions ← 哪些表被合并、哪些被排除（含原因）
#   context_files       ← 说明文档是否被正确保留
# 3) 本体体检（若使用预构建本体）
node .claude/shared/scripts/validate.mjs \
  .claude/skills/industrial-analysis-auto/schemas/ontology_schema.json \
  "workspace/bopet-data-template/03_映射文档/L3_bopet_ontology.json"
```

**本模板实测结果**（2026-10-15 复现）：

- `inspect.mjs`：主表 3024 行 × 54 列，时间列 `时间` 识别为 datetime ✅
- `data_preprocessor.py`：状态 `ok`；主表 = `L3_line_main_10min.csv`；化验表（252 行）**自动按时间合并**
  → 合并后 3024 行 × 62 列（未新增行，说明化验表时间点落在主表 10 分钟网格上）✅
- 3 份说明文档全部进入 `context/`；0 个文件被跳过；缺失率 11.83%（来自化验列的稀疏性，属预期）✅
- 预构建本体：`validate.mjs` 通过，0 错误 0 警告 ✅

## 5. 常见问题排查

| 现象 | 原因 | 处理 |
|---|---|---|
| 预处理返回 `no_tabular_data` | `data_path` 指向了包根目录（那里只有说明文档）或指错了地方 | 指向**数据文件夹**（本例 `02_data`），或直接指向某个 CSV |
| 化验/低频数据"消失"了 | 该类表 **<100 行**，不进入分析主表 | 拉长窗口使行数 ≥100，或把结论写进说明文档（见导出规范第三节） |
| 说明文档没被读进去 | 文档里写了 ≥5 行的 Markdown 表格 → 被当作数据表 | 改用列表/段落描述（本模板的说明文档即范例） |
| 时间列未被识别 | 用了 Excel 序列号、只有日期，或列名无法识别 | 改为 `YYYY-MM-DD HH:MM:SS`，列名用 `时间`/`timestamp` |
| 数值列被当文本 | 数值带了单位、千分位或 `%` | 去掉单位与符号，单位写进映射表 |
| 通篇"含义未知的列" | 代号无映射 | 补齐 `tag_mapping.csv`/`.json` 与《参数代号对照说明.md》 |
| HTML 没生成 | 审计未 `ENDORSED`（Step 7 未通过） | 看 `05_review/` 与 `optimizer.md` 的整改项；修复后重跑 8→8.5→9 |
| 结论与现场直觉不一致 | 系统以证据等级（L1–L7）+ 竞争假设协议给结论 | 对照 `04_diagnostics/evidence.json` 逐条核证据；有疑问按报告"补测建议"补充数据 |

## 6. 规模与耗时参考

- 样例规模：3024 行 × 62 列（主表 10 分钟采样 × 21 天）+ 252 行化验数据 —— 属于"小而完整"的规模；
- 真实产线 1 分钟采样 × 21 天 ≈ 3 万行 × 60 列，仍属舒适区间（系统 >10 万行时对统计做抽样）；
- 完整 `deep-diagnosis`（含修复循环与 HTML）耗时通常在 **数十分钟到 2 小时**量级（取决于引擎与模型）；
  只想快速看结论可先跑 `quick-screen`，再决定是否跑完整管线。
